Webhook и приём событий — разобрали, как сервис получает события от перевозчика через webhook. Событие сначала принимается и сохраняется, а дальнейшая обработка выполняется отдельно, чтобы не связывать получение запроса с длительной бизнес-логикой.

Идемпотентность событий — обсудили использование уникального event_id, чтобы одно и то же событие не обрабатывалось несколько раз. Такой подход защищает систему от повторной доставки webhook.

HMAC-подпись — разобрали проверку webhook через HMAC-SHA256. Сервер использует общий секрет для самостоятельного вычисления подписи и сравнивает её с подписью из заголовка, подтверждая подлинность запроса.

Worker — рассмотрели необходимость отдельного worker для обработки событий. Это позволяет вынести бизнес-логику из webhook и выполнять обработку асинхронно, с возможностью повторной попытки при ошибке.

Транзакции — разобрали применение transaction.atomic(). Изменение Shipment и изменение состояния Event должны выполняться как единая операция, чтобы при ошибке база не оставалась в частично изменённом состоянии.

Блокировка select_for_update() — обсудили ситуацию, когда несколько worker могут одновременно обработать события одного отправления. Блокировка записи Shipment предотвращает одновременное изменение её состояния.

Обработка ошибок и retry — рассмотрели поведение системы при сбое обработки события. Ошибочная транзакция откатывается, а событие остаётся доступным для повторной обработки.

Docker Compose — обсудили разделение проекта на отдельные сервисы, например Django, PostgreSQL и worker. Это позволяет запускать компоненты независимо и сохранять одинаковое окружение для проекта.

Git и расхождение веток — разобрали ситуацию, когда локальная main и origin/main содержали разные коммиты. Выяснили, что проблема была не в повреждении репозитория, а в том, что изменения были независимо сделаны локально и через GitHub.

Git rebase — рассмотрели git pull --rebase как способ поставить локальные коммиты поверх актуального состояния удалённой ветки и сохранить последовательную историю.

GitHub Actions / CI — разобрали автоматический запуск CI после git push. Workflow выполняется на GitHub runner, а его отдельные шаги и логи можно просматривать в разделе Actions репозитория.
